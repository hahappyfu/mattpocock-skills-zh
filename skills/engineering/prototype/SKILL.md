# 原型（Prototype）

原型是**回答问题的一次性代码**。问题决定了形态。

## 选择分支

识别要回答的问题，使用用户的提示、周围的代码，或者询问用户是否在：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的 HTML 文件（自由按钮加标签式引导走查），将状态机推过那些在纸上难以推理的情况，且非开发人员也能操作。
- **"这个应该是什么样子？"** → [UI.md](UI.md)。在单一路由上生成几个截然不同的 UI 变体，通过 URL 搜索参数和浮动底栏切换。

两个分支产生完全不同的产物，所以搞错会浪费整个原型。如果问题确实模糊且用户无法联系，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明假设。

## 适用于两者的原则

1. **从第一天就是一次性的，且明确标注。** 将原型代码放在它实际会被使用的地方（靠近它正在原型化的模块或页面），以便上下文显而易见，但命名要让随意浏览的人能看出来这是原型，不是生产代码。对于一次性 UI 路由，遵循项目已有的路由约定，不要发明新的顶层结构。
2. **运行极其简单。** UI 原型从项目任务运行器的一个命令开始：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是一个用户双击的 HTML 文件。无论哪种方式，都不需要思考就能启动。
3. **默认不持久化。** 状态存在内存中。持久化是原型正在*检查*的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，使用一个临时数据库或本地文件，名字要清楚标注"原型，请删除"。
4. **跳过打磨。** 没有测试，没有超出让原型*可运行*之外的错误处理，没有抽象。重点是快速学习。
5. **展示状态。** 每个动作后（逻辑）或每次变体切换时（UI），打印或渲染完整相关状态，让用户看到变化。
6. **完成时捕获。** 将任何验证过的决策融入真实代码，然后将原型本身作为**一级来源**：提交到一个从 main 分出的一次性分支，并在实施 issue 上留一个指向该分支的上下文指针。也在 issue 或提交中捕获答案（裁决和它解决的问题）。主分支只保留验证过的决策。
