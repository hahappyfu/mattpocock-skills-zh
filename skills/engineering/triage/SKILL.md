# Triage

将 issue tracker 上的 issue 通过一个小型 triage 角色状态机流转。

如果本仓库将外部 pull request 视为请求面（参见 issue-tracker 配置），triage 也会覆盖它们：**PR 就是附带了代码的 issue**，使用相同的角色、相同的状态、相同的机器，仅有几处标记为"for a PR"的差异。根据 tracker 配置，将裸的 `#42` 解析为 issue 或 PR。

在 triage 期间发布的每条评论或 issue **必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 如何撰写持久的 agent brief
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 知识库如何工作

## 角色

两个 **category** 角色：

- `bug`: 某样东西坏了
- `enhancement`: 新功能或改进

五个 **state** 角色：

- `needs-triage`: 维护者需要评估
- `needs-info`: 等待报告者提供更多信息
- `ready-for-agent`: 规格完整，可供 AFK agent 使用
- `ready-for-human`: 需要人工实现
- `wontfix`: 不会处理

对于 PR，相同的状态针对附带的代码阅读：`ready-for-agent` 意味着附带了 brief，agent 应对 diff 采取下一步操作；`ready-for-human` 意味着可供人工合并。

每个经 triage 的 issue 应恰好携带一个 category 角色和一个 state 角色。如果 state 角色冲突，标记出来并在做任何其他操作之前询问维护者。

这些是规范角色名称。在 issue tracker 中使用的实际 label 字符串可能不同。映射关系应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态流转：未贴 label 的 issue 通常先流转到 `needs-triage`；从此处再流转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回到 `needs-triage`。维护者可以随时覆盖；标记不寻常的流转并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解释请求并行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询 issue tracker 并展示三个桶，最旧的在前：

1. **Unlabeled**: 从未 triage 过。
2. **`needs-triage`**: 评估进行中。
3. **`needs-info` with reporter activity since the last triage notes**: 需要重新评估。

当 PR 在范围内时，在这些桶中包含外部 PR，并为每行标注 `[PR]` 或 `[issue]`。发现只展示*外部* PR（tracker 配置定义谁算外部），因此 collaborator 的进行中 PR 不是 triage 工作。此过滤器仅限发现；显式命名的 PR 无论作者是谁都会被 triage。

展示计数和每项的一行摘要。让维护者选择。

## Triage 特定 issue 或 PR

1. **收集上下文。** 阅读完整的 issue 或 PR（正文、评论、label、作者、日期；对于 PR，还有 diff）。解析任何先前的 triage 笔记，这样你就不会重新询问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的 ADR。对代码库运行两项检查：(a) **冗余**：按领域概念（而非仅按请求的措辞）搜索所请求行为的已有实现，并报告你搜索的位置。如果找到，这是一个已实现的 `wontfix`（步骤 5）。(b) **先前拒绝**：阅读 `.out-of-scope/*.md` 并找出任何与本请求相似的条目。

2. **推荐。** 告诉维护者你的 category 和 state 推荐及理由，加上与请求相关的简要代码库摘要（包括是否已实现）。等待指示。

3. **验证声明。** 在任何访谈之前，检查声明是否成立。对于 bug，从报告者的步骤复现。对于 PR，确认 diff 做了它声称的事情：checkout 它，运行相关测试或命令。报告发生的事情：确认（附代码路径）、失败，或细节不足（这是 `needs-info` 的强烈信号）。确认的验证会产生更有力的 agent brief。

4. **访谈（如果需要）。** 如果请求需要充实，调用 Skill 工具两次，分别用于"grilling"和"domain-modeling"，一轮问题一轮问题地访谈它，提炼领域术语并在决策落地时内联更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`: 发布 agent brief 评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`: 与 agent brief 相同的结构，但注明为何不能委派（judgement call、外部访问、设计决策、手动测试）。
   - `needs-info`: 发布 triage 笔记（模板见下方）。
   - 对于 `wontfix`，关闭 issue，评论取决于*原因*：
     - **已实现**：该改动已存在于代码库中。指向它的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝*的请求，而非已构建的）。
     - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，从评论链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`: 应用角色。如有部分进展可附可选评论。

## 快速状态覆盖

如果维护者说"move #42 to ready-for-agent"，信任他们并直接应用角色。确认你将要做的事情（角色变更、评论、关闭），然后行动。跳过访谈。如果移至 `ready-for-agent` 而没有访谈会话，询问他们是否想撰写 agent brief。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在"established so far"下捕获访谈期间解决的所有内容，这样工作就不会丢失。问题必须具体且可操作，而非"请提供更多信息"。

## 恢复先前会话

如果 issue 或 PR 上存在先前的 triage 笔记，阅读它们，检查报告者是否回答了任何未解决的问题，并在继续前呈现更新的情况。不要重新询问已解决的问题。
